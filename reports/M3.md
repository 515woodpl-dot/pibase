# M3 gate report

Date: 2026-09-30

## Result

M3 adds project-isolated filesystem storage with PostgreSQL metadata and RLS.
Objects are stored beneath `/data/files/<project>/<bucket>/<path>` while
`storage.buckets` and `storage.objects` remain the authorization source of
truth.

## Implemented

- Per-project bucket/object tables, grants, and RLS policies.
- Service-key bucket create/list/read/update/delete operations.
- Authenticated object upload, overwrite, list, download, and delete.
- Public-bucket downloads and cryptographically signed download URLs.
- Safe bucket/path validation, MIME allowlists, per-bucket file limits, and a
  configurable project storage quota (`PIBASE_STORAGE_MAX_BYTES`, default 1 GiB).
- Atomic temporary-file writes with cleanup and Compose persistent storage
  volume ownership for the non-root production image.
- Raw and multipart/Blob upload compatibility with `@supabase/storage-js`.

## Verification

- Containerized `gofmt`, `go vet ./...`, and all Go tests pass.
- Real PostgreSQL storage integration passes authenticated upload, public and
  private RLS reads, listing, signed URLs, quota rejection, and deletion.
- Real `@supabase/supabase-js` acceptance passes storage bucket creation,
  multipart Blob upload, public download, list, object removal, and bucket
  deletion in addition to the M2/data API checks.
- The distroless production image builds as `pibase:m3`.
- Static Linux ARM64 verification is run by the consolidated gate script.
- The standalone artifact `bin/pibase-linux-arm64` has SHA-256
  `c08c129ddb1b923320e73f1b67820a43fce1b194335dc342830556cf0f67b1e5`.

## Explicit boundaries

- The gateway request limit is 1 MiB; larger-object streaming/resumable upload
  is deferred.
- S3 backends, CDN invalidation, versioning, transformations, and lifecycle
  policies are outside M3.
- Bucket administration is service-key-only; customer-specific SQL policies
  can further restrict authenticated object access.
