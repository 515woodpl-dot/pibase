**Branch:** `pibase/m4-01`

## Preflight findings (2026-10-02)

- The available ARM64 host is an active Debian 13 Raspberry Pi installation,
  not a fresh disposable Raspberry Pi OS image. It was not mutated for this
  gate.
- The original package command assumed `docker-compose-plugin` existed in the
  stock distribution repository. It does not on Debian 12 or 13: Debian 12's
  `docker-compose` is legacy v1, while Debian 13 provides the v2 CLI plugin as
  `docker-compose`.
- `scripts/setup-pi.sh` now uses a packaged Compose v2 when available and
  otherwise installs the pinned official ARM64 plugin after SHA-256
  verification. It also validates `PIBASE_DATA_ROOT` before its first
  privileged command.
- `scripts/test-setup-pi.sh` exercises the packaged-v2 path, the verified
  fallback path, legacy-v1 rejection, and rejection of an unsafe data root
  without calling `sudo`.
- The consolidated `scripts/test.sh` gate passes after these changes, including
  static/unit checks, live PostgreSQL integration, the production image, and
  the Linux ARM64 build. The merged Pi Compose model also validates.

These checks reduce risk but do not satisfy M4-03. The release gate remains
open until the following procedure passes on disposable hardware.

## Disposable-Pi procedure

Use a Pi 4 with at least 4 GB RAM, a fresh 64-bit Raspberry Pi OS image, and a
USB3 SSD formatted as ext4. Do not use the active deployment host.

1. Mount the SSD at `/mnt/pibase-ssd`, clone this branch, and capture the clean
   baseline:

   ```sh
   date -Is
   cat /etc/os-release
   uname -a
   findmnt -n -o SOURCE,FSTYPE,TARGET --target /mnt/pibase-ssd
   git rev-parse HEAD
   ```

2. Run setup as the non-root operator, then log out and back in:

   ```sh
   PIBASE_DATA_ROOT=/mnt/pibase-ssd/pibase ./scripts/setup-pi.sh
   ```

3. Verify the installed host state and rerun setup to prove idempotence:

   ```sh
   docker version
   docker compose version
   systemctl is-enabled docker
   systemctl is-active docker
   id -nG
   stat -c '%U:%G %a %n' /mnt/pibase-ssd/pibase \
     /mnt/pibase-ssd/pibase/postgres \
     /mnt/pibase-ssd/pibase/files \
     /mnt/pibase-ssd/pibase/backups
   PIBASE_DATA_ROOT=/mnt/pibase-ssd/pibase ./scripts/setup-pi.sh
   ```

4. Initialize and boot the Pi deployment. Initialization generates independent
   values for `PIBASE_OPERATOR_TOKEN` and `PIBASE_BACKUP_KEY` and persists the
   selected SSD path in `.env`.

   ```sh
   PIBASE_DATA_ROOT=/mnt/pibase-ssd/pibase ./scripts/init-env.sh
   docker compose -f compose.yaml -f compose.pi.yaml up --build -d
   curl --fail http://127.0.0.1:18080/healthz
   curl --fail http://127.0.0.1:18080/metrics
   docker compose -f compose.yaml -f compose.pi.yaml ps
   ```

5. Reboot the Pi and repeat the health, metrics, and Compose status checks.
   Confirm PostgreSQL and file data still reside on the SSD. Save command
   output with the gate evidence, then wipe the disposable image.

## Pass criteria

- Both setup runs exit zero without manual package repair.
- `docker compose` is v2 or v5, Docker is enabled and active, and the operator
  receives Docker group membership after a new login.
- All four data directories are owned by the operator with mode `0750` and are
  on the ext4 USB SSD.
- The production stack builds on ARM64, becomes healthy, and remains healthy
  with persistent data after reboot.
- The captured evidence contains no `.env` contents, API keys, JWTs, operator
  token, backup key, or database password.
